Cahier des charges — Projet A : MarketPlace Analytics

Version : 3.0 (avril 2026) Pitch : pitch.md · Règles communes : Documentation commune.html

1. Contexte

Vous êtes Data Engineer dans Maelys Marketplace, une marketplace e-commerce française qui met en relation des vendeurs indépendants (artisans, marques DNVB, revendeurs) et des consommateurs finaux. Maelys prend une commission de 12% sur chaque vente.

Chiffres (fictifs) :

  • 2 400 vendeurs actifs · 180 000 produits · ~8 500 commandes/jour
  • CA mensuel ~4.2 M€
  • 75 personnes en interne dont 1 analyste qui passe 2 jours par semaine à extraire à la main les données du backoffice pour produire des rapports Excel

Le besoin

Le CEO veut un dashboard hebdomadaire avec les KPIs clés (top vendeurs, CA par catégorie, panier moyen). L'équipe finance a besoin de données fiables pour la clôture mensuelle et la facturation des commissions. Le responsable catalogue veut détecter les anomalies (drop de ventes, prix suspects).

Aujourd'hui : tout est manuel, les rapports sont en retard, les erreurs de copier-coller sont fréquentes, et l'analyste passe 40% de son temps sur de l'extraction au lieu de faire de l'analyse.

Votre mission

Construire en 2 jours un MVP de plateforme data qui :

  1. Ingère automatiquement les données depuis l'API du backoffice
  2. Les stocke dans un Data Warehouse propre (modélisation dimensionnelle)
  3. Expose des KPIs lisibles via un outil BI (Metabase)
  4. Détecte les anomalies commerciales basiques

Vous êtes l'équipe Data nouvellement recrutée. Aucune infrastructure data n'existe — vous partez de zéro. Le code doit être maintenable, testé, et reproductible (Docker Compose).

2. Objectifs pédagogiques

À la fin du projet, vous saurez :

  • 🟢 Construire un pipeline ELT idempotent end-to-end avec Airflow 3.1.8
  • 🟢 Implémenter un Custom Hook pour une API REST authentifiée
  • 🟢 Modéliser un schéma dimensionnel en étoile (Kimball)
  • 🟢 Utiliser MinIO comme zone de "raw layer" (data lake S3-compatible)
  • 🟢 Exposer des KPIs business via Metabase
  • 🟢 Brancher Prometheus + Grafana pour la supervision technique du pipeline (bonus)
  • 🟢 Tester un pipeline avec pytest

3.2 Flux d'un pipeline run

sequenceDiagram
    participant S as Scheduler
    participant H as MarketplaceAPIHook
    participant A as API Marketplace
    participant M as MinIO
    participant P as PostgreSQL
    participant MB as Metabase

    S->>H: declenche extract (date={{ ds }})
    H->>A: GET /orders?date=...
    A-->>H: JSON N commandes
    H->>M: PUT raw/orders/dt=.../data.json
    H->>P: INSERT staging.orders (idempotent)
    S->>P: DELETE + INSERT dwh.fact_orders WHERE dt = ...
    S->>P: REFRESH analytics.daily_summary
    MB->>P: SELECT pour le dashboard

3.3 Pourquoi cette architecture

  • MinIO comme raw layer : conserver le JSON brut en archive permet de rejouer un pipeline si la transformation a un bug, sans devoir re-appeler l'API source. C'est le pattern "data lake first".
  • 3 schémas PostgreSQL séparés : staging (données brutes typées), dwh (modèle dimensionnel propre), analytics (agrégations pré-calculées pour les dashboards). C'est plus propre qu'un seul schéma fourre-tout.
  • Metabase plutôt que Superset : plus simple à mettre en place, suffisant pour 4 dashboards, et l'install Docker est triviale.
  • Pas de Spark / dbt : Airflow gère lui-même les transformations SQL via PostgresHook.run(). Pour 8 500 commandes/jour, c'est largement suffisant.

5. API Marketplace (fournie)

L'API Flask simulée tourne dans un conteneur (api-marketplace) et expose ces endpoints avec authentification Bearer (formation-token-2026) :

Méthode Endpoint Paramètres Retour Notes
GET /health — {status, version} Pas d'auth requise
GET /orders date=YYYY-MM-DD liste de commandes Auth requise
GET /sellers limit liste de vendeurs Auth requise
GET /products — catalogue Auth requise
GET /customers limit liste clients Auth requise

5.1 Pourquoi cette API est "déterministe"

L'API génère ses données à partir d'un hash de la date : seed = md5(date). Conséquence : un même date = un même résultat. C'est ce qui vous permet de tester l'idempotence (rejouer un run et vérifier que les données sont identiques).

5.2 Tester l'API à la main

# Health check
curl http://localhost:5000/health

# Avec authentification
curl -H "Authorization: Bearer formation-token-2026" \
  "http://localhost:5000/orders?date=2026-04-07"

🟠 Si vous oubliez le header Authorization, l'API renvoie un 401 Unauthorized. C'est volontaire — pour vous forcer à utiliser une Connection Airflow plutôt que de hardcoder le token.

8. Modèle de données (à concevoir)

8.1 Contraintes

Vous devez concevoir vous-mêmes le schéma en étoile (Kimball). Les contraintes :

  • Schémas staging, dwh, analytics séparés
  • Au moins 3 dimensions + 1 table de faits
  • Les dimensions doivent avoir une PRIMARY KEY
  • La table de faits doit avoir des FOREIGN KEY vers les dimensions
  • Au moins 1 table d'agrégation dans analytics

8.2 Pourquoi un schéma en étoile

  • Performances : les jointures dim ↔ fait sont optimisées par PostgreSQL
  • Lisibilité : un analyste comprend immédiatement la structure
  • Reporting : Metabase est conçu pour ce modèle (auto-detection des relations)
  • Évolutivité : ajouter une nouvelle dimension ne casse rien

8.3 Conseil de design

Commencez simple :

dim_seller (id, name, country, joined_date)
dim_product (id, name, category, seller_id)
dim_date (dt, year, month, day_of_week)
fact_orders (order_id, dt, seller_id, product_id, quantity, total, commission)
analytics.daily_summary (dt, total_orders, total_revenue, top_seller_id)

🔵 Conseil : ne sur-modélisez pas. 4 tables propres valent mieux que 12 tables bancales.

Livrable : un fichier init-db/schema.sql avec vos CREATE SCHEMA et CREATE TABLE.

9.2 Custom Hook (à designer)

Le MarketplaceAPIHook doit :

  • Hériter de BaseHook
  • Lire la Connection Airflow marketplace_api (host = URL, password = token Bearer)
  • Exposer au minimum : get_orders(date), get_sellers(), get_products()
  • Gérer les erreurs HTTP (timeout, 5xx) avec un retry
  • Être testable unitairement (mock de requests)

🔵 Vous concevez la signature et l'implémentation. Ne cherchez pas un template tout prêt — c'est l'exercice.

9.3 Pattern d'idempotence (obligatoire)

Pour chaque run daté {{ ds }}, votre transformation staging → dwh doit faire :

BEGIN;
  DELETE FROM dwh.fact_orders WHERE dt = '{{ ds }}';
  INSERT INTO dwh.fact_orders
  SELECT ... FROM staging.orders WHERE dt = '{{ ds }}';
COMMIT;

Pourquoi DELETE + INSERT plutôt qu'un MERGE / UPSERT ? Parce que c'est :

  • Plus simple (pas de gestion de conflit ligne par ligne)
  • Plus performant pour des batches > 1000 lignes
  • Plus facile à débugger (la table est dans un état connu après chaque run)

Règle absolue : rejouer un run avec la même date = même résultat en base. Non négociable.

11. Découpage du projet

11.1 — Construire le pipeline ELT

L'objectif de la 1ere partie est d'avoir un pipeline qui tourne de bout en bout, même minimaliste. À la fin de la journée, vous devez pouvoir déclencher un DAG dans l'UI Airflow et constater que des données arrivent dans dwh.fact_orders.

Étapes recommandées dans l'ordre :

  1. Démarrer le stack (docker compose up -d) et vérifier que tous les services sont healthy. C'est le bon moment pour explorer l'UI Airflow et les services PostgreSQL/MinIO.
  2. Tester l'API à la main avec curl pour comprendre son format de retour. C'est plus rapide que de débugger un DAG qui appelle une API qu'on ne connaît pas.
  3. Concevoir le modèle dimensionnel sur papier ou Mermaid avant d'écrire du SQL. Identifier les dimensions et les faits, puis écrire le init-db/schema.sql. Lancez-le manuellement avec psql pour vérifier qu'il passe.
  4. Implémenter le MarketplaceAPIHook : c'est la pierre angulaire de tout le pipeline. Encapsulez l'auth Bearer (lue depuis la Connection) et exposez les méthodes get_orders, get_sellers, get_products. Testez-le isolément via un script Python avant de l'intégrer dans un DAG.
  5. Écrire le DAG d'ingestion étape par étape : commencez par une seule task qui extract et imprime le résultat. Une fois que ça marche, ajoutez l'upload MinIO (via S3Hook), puis le load dans staging.orders (via PostgresHook). Ne sautez pas d'étape — chaque task doit être validée individuellement avant de passer à la suivante.
  6. Implémenter la transformation staging → dwh avec le pattern idempotent obligatoire (DELETE + INSERT par partition dt = {{ ds }}).
  7. Tester l'idempotence : rejouer 3 fois le même run et vérifier que COUNT(*) reste identique avec psql. C'est la preuve que votre pipeline est fiable.

🟢 Objectif : pipeline principal qui tourne, idempotence prouvée, données visibles dans dwh.fact_orders. Premier commit Git poussé.

🟠 Conseil : ne sous-estimez pas le temps de design du modèle dimensionnel et du Hook. Bâcler ces 2 étapes au début vous coûtera 2x plus de temps en debug ensuite.

🟡 En cas de retard : sacrifiez le 2ème DAG (refresh dimensions). Concentrez-vous sur le pipeline principal de bout en bout.

11.2 — Analytics, dashboards, observabilité

La deuxième partie est dédié à l'exposition des données via Metabase, à la qualité du livrable (tests, doc), et éventuellement à la stack d'observabilité Prometheus/Grafana en bonus.

Étapes recommandées dans l'ordre :

  1. Construire les tables d'agrégation dans le schéma analytics. Réfléchissez à ce qui est vraiment utile pour les dashboards : daily_summary, seller_daily, category_daily. Un DAG dédié peut s'en charger.
  2. Ajouter Metabase au docker-compose.yaml avec un volume nommé pour la persistance (sinon vous perdrez tout au prochain docker compose down -v).
  3. Configurer la connexion Metabase → PostgreSQL DWH. Attention : le host est postgres-dwh (nom Docker), pas localhost, et le port interne est 5432.
  4. Créer les 2 dashboards minimum (Executive Summary + Top Sellers). Privilégiez la clarté à l'exhaustivité — un dashboard simple et lisible vaut mieux qu'un dashboard chargé.
  5. Écrire les tests pytest (au moins 3) : import sans erreur, catchup=False, structure du DAG principal. Lancez-les via docker compose exec airflow-worker pytest tests/ -v.
  6. Finaliser le README avec le schéma Mermaid de l'architecture, les instructions de lancement et les choix techniques justifiés.
  7. Bonus si avance : ajouter Prometheus + Grafana + postgres-exporter (voir §13). Importer le dashboard Grafana ID 11010 (Airflow Cluster).

🟢 Objectifs : : 2 dashboards Metabase fonctionnels, tests qui passent, README complet

🟠 Conseil : commencez la doc et les tests en parallèle du code, pas à la fin. Un README à moitié écrit en cours de route est plus efficace qu'un README rédigé en panique à 16h59.

17. FAQ

Q : On peut utiliser Superset à la place de Metabase ? R : Oui, à vos risques. Superset est plus puissant mais plus complexe. Documentez le choix dans le README. Pas de pénalité, pas de bonus.

Q : On n'a pas le temps pour les 2 dashboards Metabase, on peut skipper ? R : Un seul dashboard avec 3 visualisations est acceptable comme MVP minimal. Mais c'est risqué — ça pèsera sur la note.

Q : Le DataQualityOperator est-il obligatoire ? R : Non, c'est un bonus (Should). Concentrez-vous sur le MVP d'abord.

Q : On peut ajouter dbt pour les transformations ? R : Hors scope pour 14h. Mentionnez-le dans le README comme "ce qu'on ferait avec plus de temps".

Q : Le bonus observabilité (Prometheus/Grafana) est-il vraiment réaliste en 14h ? R : Si le MVP est fini à 14h le J2, oui : ~2h pour ajouter la stack et importer le dashboard 11010. Si vous galérez sur le MVP, n'y allez pas.

Q : Comment on accède à PostgreSQL DWH depuis l'extérieur du conteneur ? R : Le port 5433 est exposé sur l'hôte. Depuis votre machine : psql -h localhost -p 5433 -U dwh_user -d dwh. Depuis un autre conteneur : psql -h postgres-dwh -p 5432 ....

Q : Que faire si MinIO n'a pas créé le bucket ? R : Aller dans MinIO Console (http://localhost:9001, login minio_admin / minio_password_2026) et créer manuellement le bucket data-lake. Ou exécuter docker compose restart minio-init.
